# ADR-0003: 共有の入口が無いサービスには、題名と URL をコピーして投稿画面を開く操作 compose を足す

- 状態: 採用（4.1.0）
- 記録日: 2026-10-01

## 背景

読者に、記事について note・Qiita・Zenn・Medium・アメブロで書いてもらう入口を置きたい。
2026-10-01 に各サービスを確かめたところ、外部のページを共有する公式の入口（URL を渡すと投稿画面が開く口）は
note にだけあった（`https://note.com/intent/post?url=…&hashtags=…`。未ログインだとログイン画面へ 302 し、ログイン後に戻る）。
Qiita・Zenn・Medium には無く、アメブロの Ameba Now は終了している。
これらの投稿画面の URL は、Qiita `https://qiita.com/drafts/new`、Zenn `https://zenn.dev/dashboard`
（`articles/new` は 404）、Medium `https://medium.com/new-story`、アメブロ
`https://blog.ameba.jp/ucs/entry/srventryinsertinput.do` で、どれも URL で本文を渡せない。

いまの操作の種類は `open`（共有 URL を開く）・`copy`（URL をコピー）・`native`（端末の共有シート）の3つで、
入口の無いサービスはどれにも当てはまらない。ADR-0002 は「操作の種類そのものを増やす必要が出たら別の判断として扱う」としていた。

## 判断の決め手

- 目的: 入口の無いサービスでも、1回押せば「書き始められる状態」まで連れて行く。
- 目的: 共有先を足すときは、これまでどおり `destinations/<key>.toml` を1つ足すだけで済ませる。
- 制約: ポップアップブロッカーは、クリックの同期処理の外（`await` の後）で呼んだ `window.open` を止める。
- 制約: クリップボードへの書き込みは非同期で、拒否されることがある。書き込みの完了前に成功を名乗らない。
- 制約: 依存の向き（domain ← application ← presentation、domain ← infrastructure）を崩さない。

## 検討した選択肢

1. **`open` のまま投稿画面を開くだけ**: 追加の実装が要らない。一方で、開いた画面に記事の題名も URL も無く、
   読者は元のタブへ戻って URL を探すことになる。→ 目的を満たさないので捨てた。
2. **`copy` で URL をコピーするだけにし、投稿画面は読者に開いてもらう**: 窓を開かないのでブロックされない。
   一方で、どのサービスのボタンを押しても同じ動きになり、共有先として並べる意味が無い。→ 捨てた。
3. **投稿画面の URL にクエリで題名や本文を付ける**: 1回で済む。一方で、確かめた4サービスはどれもクエリを読まない。
   読まない項目を送るのは、動くように見えて何も起きない沈黙の失敗になる。→ 捨てた。
4. **新しい操作 `compose`: 題名と URL をクリップボードへ書き、同時に投稿画面を新しいタブで開く**: 採用。

窓の開き方は、次の2案を比べた。

- (a) 既存の `open` と同じく設定（`behavior.popup`・`behavior.open_in_new_tab`）に従う。
- (b) 設定に関わらず、常に新しいタブで開く。

(b) を採った。理由は3つある。小窓（600×500 程度）はエディタを使うには狭く、ログイン画面への転送も挟まる。
同じタブで開くと元の記事が画面から消え、貼り付けた内容を見比べられない。
さらに、同じタブで移動するとクリップボードへの書き込みの完了を待つページが無くなり、成功・失敗を知らせられない。

## 決定

操作の種類に `compose` を足す。

- 宣言: `destinations/<key>.toml` に `action = 'compose'` と、`https://` で始まる投稿画面の URL を `endpoint` に書く。
  URL に項目を送らないので `[params]` は書かせない（空の表でも止める）。生成器 `tools/config.py` がこれを検査する（fail closed）。
- 文面: 「ページの題名＋改行＋共有 URL」。URL には他の共有先と同じ UTM を付ける（`utm_source` は共有先の識別子）。
  題名が空なら URL だけにする。決めるのは domain の `ShareActionPolicy.composeDraft()`。
- 順序: `HandleShareClickUseCase` は、クリップボードへの書き込みと新しいタブを開く処理の両方を、最初の `await` より前に呼び始める。
  書き込みを先に始め、同期で例外が出ても拒否として扱うので、投稿画面は必ず開く。
- 窓: 常に新しいタブ（`noopener,noreferrer`）。domain の `ShareWindowGateway` に `openTab()` を足し、infrastructure が実装する。
- 通知: 成功は `messages.composed`、失敗は `messages.compose_failed` を既存の画面内通知で出す。
  どちらも省略でき、省略すると既定の文言を使う（既存の設定ファイルはそのまま通る）。
  失敗しても `copy` のような `prompt` は出さない。読者の目はすでに新しいタブにあり、元のページのダイアログは見えないからである。
- 表示: `compose` はリンクではなくボタンとして描く（既定の共有欄・円い共有欄の両方）。

note は公式の入口があるので `compose` にせず、`open` の共有先として足す。

## 結果

- 良い: 入口の無いサービスでも、1回押せば投稿画面が開き、貼り付けるだけで書き始められる。
- 良い: 共有先の追加は TOML を1つ足すだけのまま（Qiita・Zenn・Medium・アメブロは各8行）。
- 良い: 既存の `open`・`copy`・`native` の動きと、既存の設定ファイルは変わらない（後方互換なので 4.1.0）。
- 悪い: 投稿画面の URL はサービスの都合で変わりうる。入口ではないので、変わっても予告は無い。
  `articles/new` が 404 だった Zenn のように、確かめた日付（2026-10-01）ごと記録し、見直す。
- 悪い: 新しいタブが開けたかどうかは、ページから観測できない（`noopener` で開いた窓の参照は返らない）。
  ブロックされたときに知らせる手段が無い。
- 悪い: ブラウザによっては、新しいタブへ焦点が移ったあとにクリップボードへの書き込みが「文書に焦点が無い」として拒否されうる。
  その場合も投稿画面は開き、失敗の通知を出す。
- 悪い: `behavior.popup`・`behavior.open_in_new_tab` が `compose` には効かない。設定の説明に明記した。

## 見直す条件

- どれかのサービスが外部ページを共有する公式の入口を用意した（その共有先は `open` へ移す）。
- 投稿画面の URL が変わった、またはログイン後に投稿画面へ戻らなくなった。
- クリップボードへの書き込みの失敗が多いと分かった（焦点の移動による拒否など）。
- 文面（題名＋改行＋URL）以外を貼りたいという要望が出た（引用や説明文を足すなど）。
