# ADR-0002: 共有先を destinations/<key>.toml のデータで宣言する

- 状態: 採用（4.0.0）
- 記録日: 2026-09-25
- 置き換えたもの: 記録の無かった「共有先は PHP のクラスで書く」（1.0.0〜3.2.0）

## 背景

1.0.0 では PHP がボタンを描き、共有 URL も組み立てていたので、共有先を PHP のクラスで書く理由があった。
2.0.0 で URL の組み立てをブラウザ側の1か所へ移したあと、クラスは「どこへ何を送るか」の宣言だけに縮んだ。
WordPress の実行時には読み込まれず、生成器（`tools/config.py`）が正規表現で文字を拾うだけになっていた。
そのため、PHP として正しく書いても、定数や文字列の連結を使うと生成器だけが止まる。実行されないので、型の検査も効いていない。
PHP で書く理由は 2.0.0 の時点で消えていたが、その理由がどこにも記録されていなかったため、形だけが残った。

## 判断の決め手

- 目的: 共有先を1つ足すとき、1ファイル足すだけで済む形（差し込み口）を保つ。
- 目的: 書き間違いを、生成の時点で止める（知らない項目も止める）。
- 制約: 設定を検証する生成器は Python で、設定の TOML も `tomllib` で読んでいる。
- 制約: 配布物（`dist/promari-sns-share.min.js`）を変えず、サイト側の変更を不要にする。

## 検討した選択肢

1. **PHP のクラスのまま**: 変更は要らない。一方で、実行されないコードの形をしたデータを正規表現で読み続けることになる。→ 捨てた。
2. **TypeScript で宣言する**: 型の検査が効く。一方で、設定を検証する Python の生成器から読みにくく、同じ問題が残る。→ 捨てた。
3. **1つの JSON にまとめる**: 読みやすい形式。一方で、共有先を足すたびに同じファイルを書き換えることになり、1ファイル足すだけの差し込み口がなくなる。→ 捨てた。
4. **共有先ごとの TOML ファイル**: 採用。

## 決定

共有先を `destinations/<key>.toml` に1件1ファイルで宣言する。生成器は `tomllib` で読み、
未知の項目・ファイル名と `key` の不一致・未知の操作の種類・未知の送り項目を見つけたら止める。
PHP の `Destination` クラス、`ShareDestinationInterface`、`ShareAction` は削除する。

## 結果

- 良い: 架空の共有先を1件足す実験で、定義の行数が PHP のクラスの53行から TOML の11行（コメント・空行を含む）になった。
- 良い: 生成されるカタログと配布物は、変更前とバイト単位で一致した（サイト側の変更は不要）。
- 良い: `key` とファイル名をそろえる検査により、同じ名前の共有先が2つある状態を作れなくなった。
- 悪い: PHP で独自の共有先を足していた利用者には移行が要るので、メジャー版（4.0.0）にした。
- 悪い: アイコンの SVG を TOML の文字列に入れるので、長い1行になる。

## 見直す条件

- 共有先の定義を、実行時に読みたい場面が出た（例: 管理画面から共有先を足したい）。
- 生成器を Python 以外へ移すことになった。
- クリックで何をするかの種類（open・copy・native）そのものを増やす必要が出た（別の判断として扱う）。
