# ADR-0001: 共有ボタンを Web Components として作る

- 状態: 採用（1.0.0 で導入。2.0.0 で WordPress 側の描画をやめ、この要素に一本化）
- 記録日: 2026-09-26（判断は 1.0.0 当時。当時の記録が無かったため、CHANGELOG と解説記事から書き起こした）

## 背景

以前の共有欄は、各 SNS の公式ウィジェット（iframe）だった。iframe の中は別の文書なので、
ボタンのフォントや余白を自サイトの CSS でそろえられない。枠の中で押されたクリックも、
親ページでいつもどおりイベントを見張るだけでは受け取れず、どのボタンが使われたかを数えられなかった。

## 判断の決め手

- 目的: 静的な HTML と WordPress の両方に、同じ部品を置きたい。
- 目的: 見た目とクリックの計測を、自分たちが管理できる範囲に置きたい。
- 制約: 設置する側（ホスト）に、特定のフレームワークや実行環境を要求しない。
- 制約: SNS 側の投稿処理までは作らない。持つのは、共有画面へ渡す入口まで。

## 検討した選択肢

1. **公式ウィジェット（iframe）のまま**: 共有 URL の変更や端末ごとの違いの保守を各社に任せられる。
   一方で、見た目とクリックの計測が自分たちの管理範囲に入らない。→ 目的を満たさないので捨てた。
2. **React などの UI フレームワークの部品として作る**: 部品の書きやすさは高い。一方で、設置する側に
   そのフレームワークの読み込みやビルドを求めることになり、静的な HTML へそのまま置けない。→ 制約に反するので捨てた。
3. **WordPress（PHP）でボタンを描く**: WordPress の中では完結する。一方で、静的な HTML では使えず、
   ブラウザ側にも同じ処理が要るため二重の実装になる。→ 1.0.0 では併用したが、2.0.0 でやめた。
4. **Web Components（Custom Elements と Shadow DOM）で独自要素を作る**: 採用。

## 決定

共有欄を独自要素 `<promari-sns-share>` として作り、ブラウザ用の JavaScript を版を固定した CDN から配る。
WordPress のプラグインは、この要素を出力するだけにする（2.0.0）。

## 結果

- 良い: 同じ要素を静的な HTML にも WordPress にも置ける。
- 良い: Shadow DOM の中で描くので、テーマ側のボタン用 CSS と偶然ぶつかりにくい。
- 良い: クリックを部品自身が `promari-sns-share` イベントとして知らせるので、計測を自分たちで持てる。
- 悪い: 共有 URL の形式の変更、端末ごとの違い、アクセシビリティを、自分たちで保守する。
- 悪い: 外側から Shadow DOM の中のリンクを見張れないので、イベントの名前と中身を約束として守り続ける必要がある。

## 見直す条件

- 保存先が増えた、または変わった（いいねの保存先など）。
- 対応する端末やブラウザの範囲が変わった。
- 公式ウィジェットに、見た目の調整やクリックの観測に必要な機能が備わった。
