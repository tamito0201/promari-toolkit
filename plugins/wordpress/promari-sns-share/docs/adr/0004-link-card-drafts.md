# ADR-0004: 共有先ごとに「そのサービスのリンクカード・埋め込みの書き方」で記事を紹介する

- 状態: 採用（4.2.0）
- 記録日: 2026-10-01
- 改めたもの: [ADR-0003](0003-compose-action.md) の「文面は題名＋改行＋URL」（アメブロは `compose` から `open` へ移した）

## 背景

4.1.0 の `compose` は、どの共有先でも「題名＋改行＋URL」をコピーしていた。貼った結果は、どのサービスでも
ただの文字とリンクで、記事の題名・説明・画像を持つカードにはならなかった。
2026-10-01 にログイン済みのブラウザで各サービスの投稿画面を確かめたところ、次のことが分かった。

| 共有先 | 実測 | 採った形 |
|---|---|---|
| アメブロ | 投稿画面 `https://blog.ameba.jp/ucs/entry/srventryinsertinput.do` は `entry_title` と `entry_text` のクエリを読み、題名と本文を事前入力する。本文に Ameba のリンクカードの HTML を渡すと、エディタにカードとして表示される。長すぎる URL は 400 になる（上限は次の節） | `compose` をやめて `open` にし、`entry_title` に題名、`entry_text` にカードの HTML を送る（コピーしない） |
| Qiita | 「題名＋空行＋URL＋空行」を本文に貼ると、プレビューで URL がリンクカード（Qiita の埋め込み iframe）になる。4.1.0 の「題名＋改行＋URL」は空行が足りずカードにならない。`drafts/new?title=&body=` はクエリを読まない | `compose` のまま、コピー文を `{title}\n\n{url}\n` にする |
| Zenn | 本文に `@[card](URL)` を貼ると、プレビューでカード（embed.zenn.studio の iframe）になる。事前入力の口は無い | `compose` のまま、コピー文を `{title}\n\n@[card]({url})\n` にする |
| Medium | 公式ヘルプ「Using embeds」は「新しい行に URL を貼り、Enter を押すと埋め込みになる。対応外のサービスはプレビューのカードになる」とする。「題名＋改行＋URL」を貼ると、Medium は2行を1つの段落（段落内の改行）にまとめ、URL が単独の行にならないので Enter を押してもカードにならなかった。URL だけを空の行に貼って Enter を押すと、題名・説明入りのカード（mixtapeEmbed）になった。`new-story` は title・body・content・text・url のどのクエリも読まない | `compose` のまま、コピー文を `{url}` だけにし、成功の知らせに「貼り付けたあと Enter を押すと、記事のカードになります」を足す |
| note | 公式の入口 `intent/post` がある | 変更しない |

### URL の上限の根拠

アメブロの上限は URL 単独ではなく、URL とクッキーなどを合わせた**リクエスト全体**の大きさで決まる。2026-10-01 に二分探索で確かめた。

| 状態 | アメブロへ送るクッキー | 通った URL | 400 になった URL |
|---|---|---|---|
| ログインしていない | ほぼ無し | 6,000 文字まで（ログイン画面へ 302） | 8,000 文字 |
| ログイン済み | 約1,800 文字 | 5,105 文字まで | 5,140 文字 |

ログインの有無で通る長さが約1,000 文字以上ずれるのは、クッキーの分だけリクエストが大きくなるからである。
クッキーの量は読者ごとに違い（ログインの状態・閲覧履歴・広告の計測など）、ページからは測れない。
そこで、下書きを送る URL の上限を **3,500 文字**にした。ログイン済みで通った 5,105 文字との差は約1,600 文字で、
今回の読者よりクッキーが約1,600 文字多い読者（合計約3,400 文字）まで通る見込みになる。
4.2.0 の最初の案は 2,900 文字だったが、promari.jp の記事の題名は末尾に「| プロマリのブログ」が付いて約70文字あり、
2,900 文字では説明と画像が外れ、題名も67文字に縮んだ（下の「結果」の表）。

Medium には記事の取り込み（`medium.com/p/import`）もあるが、公式ヘルプはこれを「取り込む権利を持つコンテンツに限る」としている。
読者が他人の記事を紹介する用途には当たらないので使わない。

## 判断の決め手

- 目的: 入口の無いサービスでも、開いた先のサービスが持つ埋め込み機能を使い、記事をカードとして紹介してもらう。
- 目的: 共有先の追加・変更は、これまでどおり `destinations/<key>.toml` のデータだけで済ませる（コードに共有先の名前を書かない）。
- 制約: 書き間違いや、宣言したのに使われない項目は、生成の時点で止める（fail closed）。
- 制約: アメブロの投稿画面は長すぎるリクエストを 400 で拒む。上限は読者のクッキーの量で動くので、余裕を持たせた上限を超える URL を作らない。
- 制約: 依存の向き（domain ← application ← presentation、domain ← infrastructure）と、domain がブラウザ API を知らないことを保つ。

## 検討した選択肢

1. **共有先ごとの文面をコードに書く（`if (key === 'ameba')` など）**: すぐ書ける。一方で、共有先の名前がコードに入り、
   共有先を足すたびにコードを直すことになる。ADR-0002 の差し込み口がなくなる。→ 捨てた。
2. **コピー文だけを差し替え、アメブロも `compose` のまま**: 変更は小さい。一方で、アメブロは投稿画面が本文を受け取れるのに、
   読者に貼り付けの手間を残し、カードの HTML は貼り付けではエディタにカードとして入らない。→ 捨てた。
3. **Medium の取り込み（`p/import`）を使う**: 記事がそのまま取り込まれる。一方で、取り込めるのは権利を持つ内容に限られる。→ 捨てた。
4. **共有先の TOML に、そのサービスでカードになる書き方を「下書きのひな形」として宣言する**: 採用。

## 決定

- 宣言: `destinations/<key>.toml` に任意の `draft`（ひな形）と `draft_format`（`text` か `html`）を足す。差し込み口は
  `{title}`・`{url}`・`{description}`・`{image}`・`{host}` だけで、それ以外の差し込み口や単独の波括弧は生成器が止める。
  `draft` と `draft_format` は両方書くか両方書かない。`draft` を書けるのは `open` と `compose` だけで、`open` は `[params]` で
  `'draft'` を送らなければ止める（宣言したのに使われない下書きを作らない）。逆に `'draft'` を送るのに `draft` が無ければ止める。
- 送り項目: `[params]` の値に `draft`（その共有先の下書き）を足す。アメブロは `entry_title = 'title'`・`entry_text = 'draft'`。
- 組み立て: domain の値オブジェクト `ShareDestination` が、ドメインサービス `DraftTemplate`（差し込み・`html` なら値ごとの
  HTML エスケープ・`text` なら先頭の空行を残さない）で下書きを作る。`draft` の無い `compose` は、従来どおり「題名＋改行＋URL」。
- ページの説明と画像: infrastructure の `BrowserSharedPage` が `og:description`（無ければ `meta[name=description]`）と
  `og:image`（http・https の絶対 URL に解決できたものだけ）を読み、domain の `SharedPage` に値として渡す。要素の
  `description`・`image` 属性で上書きできる（`url` 属性で別の記事を指すときのため）。
- 長さの上限: ドメインサービス `LinkCardPolicy` が、下書きに入る題名を100文字、説明を60文字で切り（末尾は「…」）、
  下書きを送る共有 URL を 3,500 文字以内に収める（根拠は「URL の上限の根拠」）。超えたら、説明を縮めてから外し、次に画像を外し、最後に題名を縮める。
  依頼時の仕様は「説明 → 画像の順に落とす」だったが、実測で、それだけでは足りないことが分かったので題名を縮める段を足した
  （次の「結果」の表）。説明も、丸ごと外す前に収まる長さまで縮める。
- 窓: 下書きを送る `open` の共有先は、サービスの投稿画面を開く。ADR-0003 と同じ理由（小窓はエディタに狭い）で、
  `behavior.popup` が `true` でも小窓にしない。判断は domain の `ShareActionPolicy.canOpenInPopup()` の1か所に置く。
- 知らせ: `compose` の共有先の TOML に任意の `compose_hint` を足し、成功の知らせの後ろに付ける（Medium に日本語の既定文）。
  既定の `messages.composed` は、Medium が URL だけをコピーするようになったので「記事のリンクをコピーしました。投稿画面に貼り付けてください」に改めた。

## 結果

- 良い: Qiita・Zenn は貼るだけで、Medium は貼って Enter で、アメブロは開いただけで、記事がカードとして入る。
- 良い: 共有先の名前はコードに無い。4つの変更はどれも TOML の書き換えで、生成器が差し込み口・書式・使われない宣言を検査する。
- 良い: `draft` を書かない共有先の生成物は 4.1.0 と同じ形のまま（`draft`・`composeHint` は宣言したときだけ出る）。
- 悪い: アメブロの URL は、日本語の題名だと上限に届きやすい。日本語1文字は符号化で9文字になり、題名は `entry_title` と
  カードの両方に入るので、1文字あたり約18文字を使う。記事 URL が約100文字（UTM 込み）、画像 URL が約80文字、説明が日本語60文字のときの実測は次のとおり（上限 3,500 文字）。

  | 題名 | URL の長さ | 残った題名 | 残った説明（最大60） | 画像 |
  |---|---|---|---|---|
  | 日本語30文字 | 2,890 | 30 | 60 | 残る |
  | 日本語60文字 | 3,430 | 60 | 60 | 残る |
  | 約70文字（日本語59文字＋「 \| プロマリのブログ」） | 3,493 | 70 | 51 | 残る |
  | 日本語70文字 | 3,493 | 70 | 47 | 残る |
  | 日本語90文字 | 3,493 | 90 | 7 | 残る |
  | 日本語100文字 | 3,499 | 99 | 0 | 外す |

  参考までに、最初の案の上限 2,900 文字では、約70文字の promari.jp の題名で説明と画像が外れ、題名も67文字に縮んだ。
  説明と画像を外しても収まらない長さでは題名を縮める段が要る（依頼時の「説明 → 画像」だけでは 400 になりうる）。
- 悪い: 画像を外したカードは `<img src="">` を持つ。ひな形には、値が空のときに一部を消す仕組み（条件付きの区間）が無いので、
  空の画像枠が残りうる。上限 3,500 文字では、画像が外れるのは日本語の題名が約100文字に達したときだけになる。
- 悪い: 3,500 文字の余裕を超えるクッキーを持つ読者には、上限内の URL でも 400 になりうる。ページからクッキーの量は測れないので、防げない。
- 悪い: 記事 URL が英数字だけで約1,900文字を超えると（実測 1,923 文字まで収まる）、題名を空にしても収まらない。そのときは最も短い URL を返すので、アメブロは 400 を返しうる。
- 悪い: アメブロのカードの HTML・投稿画面のクエリ名は、公開された仕様ではない。予告なく変わりうるので、確かめた日付（2026-10-01）ごと記録した。
- 悪い: Medium のカードは、読者が Enter を押すまでできない。知らせで伝えるが、見落とされうる（知らせは文字数に応じて最長6秒出す）。
- 悪い: `html` の下書きは値を HTML エスケープするが、ひな形そのものは検査しない。ひな形の HTML は TOML を書く人の責任になる。

## 見直す条件

- アメブロの投稿画面が `entry_title`・`entry_text` を読まなくなった、カードの HTML の形が変わった、またはリクエストの上限が変わった。
- ログイン済みの読者から 400 の報告が出た（クッキーが見込みより多い。上限 3,500 文字を下げる）。
- Qiita・Zenn・Medium のカードの書き方（空行・`@[card]`・Enter）が変わった、またはどれかが本文を受け取る入口を用意した（その共有先は `open` へ移す）。
- 空の画像枠が問題になった（ひな形に条件を持たせるか、画像を外す段をやめるかを決める）。
- 下書きを送る共有先を、小窓で開きたいという要望が出た。
